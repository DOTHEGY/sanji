# Partyum custom Seoul scheduling
The owner selects the reserve date and time in each discovery-day group. A reservation preserves the existing server-selected eligibility, reviewed copy, exclusion, duplicate, authentication and idempotency gates. Groups may share a due timestamp, but each needs its own preview and confirmation. Rates and evidence are rechecked during actual dispatch; the selected time marks eligibility for sequential sending, not simultaneous Gmail receipt.

The repository's checked-in historical bundles are not the live baseline. Do not deploy them over the owner-safe endpoint. Before an authorized rollout:
1. Obtain fresh verified `youtube-wedding-mail` endpoint source and confirm the current version. The local-only `prepare-v8-custom-schedule.mjs` accepts only the exact tested v8 sources and copies the incident module byte-for-byte. A changed live source requires review rather than forcing the transform.
2. Validate the migration against an isolated DB clone; widen only the private batches mode CHECK. Do not change grants, users, sender setup, worker policy, status endpoint or global/product gates. Apply the migration before enabling the new mail route. Leaving the widened CHECK in place during rollback preserves already queued custom reservations.
3. Validate the additive mail bundle, then publish in an authorized release with the pre-existing JWT policy and both preserved files. The unchanged status and worker routes already interpret non-immediate batches by stored due timestamp. No transport or config change is part of this feature.
4. Publish the browser assets after confirming the updated mail endpoint. Smoke-test authenticated plan only in production. No live schedule/submit without explicit separately authorized scope.
5. Recovery: remove or revert the new UI/route if needed; do not drop the schema widening while custom records remain. Before ever retrying a request, verify persisted attempts and do not convert scheduled work to immediate.
