# 실제 운영 버전: 배포·계정 연결

## 현재 구현과 검증 경계

운영 코드: `api/`, `private/ui/`, `server.cjs`. 공개 데모는 `public/`이며 GitHub Pages에는 이 디렉터리만 공개합니다. **GitHub Pages에서 실제 업무 서버는 실행되지 않습니다.** 서버를 배포하면 루트는 `/app/`으로 이동합니다. 운영 자료 API는 모두 로그인 뒤에 있습니다. 운영 UI 셸은 공개 파일이지만 후보·가격·연락처·메시지는 포함하지 않습니다.

운영 DB는 처음에 비어 있습니다. 가상 회사나 임의 이메일을 실제 후보처럼 채우지 않습니다. 확인한 공식 링크·제품·크리에이터 계정을 등록하고 출처·확인일을 기록할 수 있습니다. 공개 검색은 Brave Search API 연결 시 실제 결과를 표시하며, 키가 없으면 검색 제공자 페이지를 여는 대체 링크를 제공합니다. 공식 도메인이나 이메일 소유권을 자동으로 검증한다고 주장하지 않습니다. 수치·관계·공식 연락처 확인은 사람의 검증 단계입니다.

자동 검증: 인증, 초기 계정 보호, CSRF, API 비인가 접근 차단, 회사·계정·연락처 중복, 팔로워 출처 필수, 딜 버전 보존, 모호한 효능 문구 차단, 고정 미리보기 승인, 발송 비활성 스위치, 수동 DM 기록, 수신 거부 차단, Gmail MIME·첨부 생성/수신 동기화/불확실한 결과의 재시도 방지(모의 제공자), 운영 UI 브라우저 저장·새로고침·모바일. **실제 Google/Meta 계정 연결·송수신은 인증 정보가 없어 미검증**입니다. Gmail 공급자 응답 모의 검증은 실제 전달 검증이 아닙니다.

## Render에 올리기 (사용자 작업·요금 승인 필요)

Render 계정과 결제는 아직 연결하지 않았습니다. `render.yaml`은 Starter 서버와 1GB 영구 디스크를 선언합니다. 무료 임시 파일 시스템으로 실제 영업 자료가 사라지는 것을 피하기 위한 구성입니다. **실제 가격을 확인하고 별도로 승인한 뒤 배포하세요. 에이전트는 결제·서버 생성을 진행하지 않았습니다.** Render의 현재 가격 및 영구 디스크·백업 조건은 Render 대시보드에서 확인해야 합니다.

1. https://dashboard.render.com/ 에서 가입하고 GitHub 저장소 접근을 연결합니다. 최소 `DOTHEGY/sanji` 저장소만 허용하면 됩니다.
2. New → Blueprint에서 이 저장소의 `main`을 선택합니다. `render.yaml`의 비용·서비스·디스크 항목을 검토합니다. 이 단계에서 유료 생성을 승인하지 않았다면 중단합니다.
3. Render가 제공하는 RENDER_EXTERNAL_URL을 기본 주소로 자동 사용합니다. 자체 도메인을 쓰면 APP_URL을 해당 HTTPS 주소로 명시하세요. GOOGLE_CLIENT_ID/GOOGLE_CLIENT_SECRET은 아래 Google 설정 후 서비스의 비공개 환경 변수로 추가합니다. OAuth 설정을 나중에 해도 서버는 시작하며 Gmail 연결 기능만 비활성입니다.
4. SANJI_ENCRYPTION_KEY와 SANJI_SETUP_TOKEN은 Render가 별도 난수로 생성합니다. 키는 외부 토큰 암호화에 사용하므로 백업과 함께 안전하게 보관하고 임의로 바꾸지 마세요. 키를 바꾸면 저장한 OAuth 연결을 복구할 수 없습니다.
5. `/healthz`가 `{ "ok": true }`인지 확인합니다. `/app/`에서 초기 관리자 이메일·새 서비스 비밀번호(12자 이상)·SANJI_SETUP_TOKEN으로 계정을 생성합니다. 첫 관리자 생성 후 초기 가입은 자동으로 닫힙니다. 메일 계정 비밀번호를 입력하지 않습니다.
6. 재시작 후 로그인·후보 저장 유지까지 검증합니다. 현재 구조는 단일 서버·단일 관리자용 MVP입니다. 여러 서버로 수평 확장하면 SQLite·발송 제한·세션 구조를 별도 DB/큐로 옮겨야 합니다.

로컬 검증:

```sh
npm ci --cache /tmp/sanji-npm-cache
DATA_DIR=/tmp/sanji-local npm start
```

로컬 개발에서는 초기 토큰과 암호화 키를 지정하지 않으면 DATA_DIR 내부 권한 제한 파일로 생성됩니다. `setup.token` 값을 로컬에서만 확인해 초기 관리자 생성에 사용합니다. 채팅·Git·공개 문서에 붙이지 마세요. 운영 NODE_ENV=production에서는 APP_URL 또는 RENDER_EXTERNAL_URL(HTTPS), SANJI_ENCRYPTION_KEY, SANJI_SETUP_TOKEN이 반드시 필요합니다.

## Gmail / Google Workspace

1. 본인의 Google Cloud 프로젝트에서 Gmail API를 활성화합니다.
2. Google Auth Platform에서 앱 정보·대상 사용자·동의 화면을 구성합니다. 내부 Workspace 앱이면 조직 정책을 확인합니다. 외부 테스트 앱이면 실제 연결할 본인 계정을 테스트 사용자로 등록합니다.
3. OAuth 클라이언트 유형 `웹 애플리케이션`을 만들고 승인된 리디렉션 URI를 `https://실제서버주소/oauth/gmail/callback`으로 등록합니다. URI는 서버 APP_URL과 완전히 일치해야 합니다.
4. `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`을 Render 비공개 환경 변수로 입력합니다. 이 값들은 GitHub Pages나 채팅에 입력하지 않습니다.
5. 운영 서비스 → 연동 설정 → Google 공식 로그인에서 계정을 연결합니다. 코드가 요청하는 범위는 `gmail.send`, `gmail.readonly`입니다. Gmail 읽기는 제한된 범위이므로 외부 운영 앱에 Google 검증·경우에 따른 추가 보안 평가가 필요할 수 있습니다. 테스트 앱의 갱신 토큰 수명 제한 및 계정 한도도 확인하세요. 검증·평가 비용은 현재 산정하지 않았습니다.
6. 발신자명·주소·연락처를 저장합니다. 수신 거부 회신 안내는 하단에 자동 포함됩니다. 광고성 제목은 `(광고)`로 시작해야 하며 한국시간 08~21시 외에는 차단합니다. 야간 별도 동의 예외는 미구현입니다.
7. **실제 발송 별도 승인 후에만** `EMAIL_SENDING_ENABLED=true`를 서버에 설정합니다. 기본값 false입니다. 특정 수신자·카피·첨부에 대한 서비스 내 최종 승인도 매번 필요합니다. 실제 발송 테스트는 승인된 본인 테스트 수신자부터 시작해야 합니다.

이메일 발송은 개별 수신자 단위입니다. 여러 수신자에 대한 무검토 일괄 발송은 제공하지 않습니다. Gmail API 접수는 도착/열람이 아닙니다. API 확정 거부는 provider_rejected, 타임아웃·처리 불확실은 outcome_unknown으로 남기고 자동 재시도하지 않습니다. 승인 미리보기는 15분 유효하며 대상·상품 버전이 바뀌면 새 승인이 필요합니다. 승인 전 파일 내용을 사용자 브라우저가 읽어 서버로 보내며, 첨부 합계 5MB·파일당 2MB·5개 제한입니다.

수신 동기화는 등록한 후보 이메일과 최근 90일 대화를 읽습니다. 대상 30명·대상당 대화 20개로 제한되며 일부 결과일 때 표시합니다. 첨부가 있는 수신 메일의 파일 다운로드는 Gmail 원본에서 확인합니다. HTML 전용 메일은 제공자의 snippet만 보여줄 수 있습니다. 원격 MIME의 auto-submitted/precedence 등으로 자동 응답을 구분하고, 사람 회신의 명시적 수신 거부 요청을 차단 목록에 반영합니다. 자동 분류에는 한계가 있으므로 답장 분류와 Gmail 원본을 확인하세요. 운영 초기에 동기화 버튼을 자주 사용해야 하며 백그라운드 Gmail push 알림은 아직 구현하지 않았습니다.

기존 메일 이력이 알려지지 않은 상태에서 중복 연락할 수 없도록 **영업 시작 전에 후보를 등록하고 Gmail 대화를 먼저 동기화하세요.** 서비스가 알지 못하는 외부 채널/과거 연락까지 자동으로 파악할 수는 없습니다.

## Instagram

2026-10-21 공식 메시징 문서에서 상대 사용자가 먼저 대화를 시작해야 한다는 조건을 확인했습니다. 일반적인 메시징 창은 24시간입니다. 일부 Click-to-Direct 광고 경로의 더 긴 시간 예외를 이 MVP에서는 사용하지 않습니다. 신규 선제 DM은 수동 문구 복사·프로필 열기·직접 발송 결과 기록으로 제공합니다. 개인 계정 로그인 우회나 비밀번호 수집은 없습니다.

- Meta 앱의 Instagram API with Instagram Login을 설정하고 프로페셔널 계정을 연결해야 합니다. `instagram_business_basic`, `instagram_business_manage_messages` 범위를 요청합니다. 다른 사업자의 계정을 서비스하려면 Advanced Access/앱 심사 등 요구 조건을 확인하세요.
- `META_APP_ID`, `META_APP_SECRET`, `META_VERIFY_TOKEN`을 서버의 비공개 환경 설정에 입력합니다. 현재 기본 Graph 버전은 v24.0이며 앱 대시보드에서 지원 버전을 확인 후 META_GRAPH_VERSION으로 명시하세요.
- 공식 인증 리디렉션 URI: `https://실제서버주소/oauth/instagram/callback`
- 웹훅 주소: `https://실제서버주소/api/instagram/webhook`. Verify Token은 META_VERIFY_TOKEN과 일치하도록 설정합니다. 메시지 웹훅을 구독해야 읽기가 동작합니다. 수신 payload는 앱 시크릿 HMAC 서명으로 검증하고 message ID로 중복을 막습니다.
- 계정에서 시작되지 않은 새 대화는 생성/전송하지 않습니다. 인바운드 대화의 Instagram-scoped sender ID를 저장하고, 운영자가 공개 프로필과 후보의 관계를 직접 확인해 연결해야 합니다.
- 실제 회신도 별도 승인 후 `INSTAGRAM_SENDING_ENABLED=true`로 활성화해야 합니다. 서버는 최근 24시간 안에 수신된 대화에만 답장하며 1000바이트 이하 텍스트만 지원합니다. 외부 계정 인증과 실제 웹훅 수신은 미검증입니다.
- 토큰 자동 갱신·첨부 DM·메시지 폴더 구분·과거 전체 대화 가져오기는 미구현입니다. 토큰 만료 시 공식 재연결해야 합니다. API 응답 접수를 임의로 전달/열람으로 표시하지 않습니다.

공식 원문: https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/messaging-api/

## 실제 후보 검색

Brave Search API 계정에서 발급한 키를 `BRAVE_SEARCH_API_KEY`로 서버에 연결하면 검색 결과 제목·URL·설명·확인 시점을 제공합니다. 키가 없으면 실제 Google 검색 링크와 직접 추가 경로가 동작합니다. 검색 제공자 유료 플랜 결제는 하지 않았습니다. 결과를 이메일/계정 검증 완료로 표시하지 않으며, 검색 결과만으로 팔로워·실판매·질병 상태를 추정하지 않습니다. 연락처는 공식 페이지 출처·소유 회사·사업 목적을 사용자가 검증해야 사용 가능해집니다.

## 운영의 현재 한계·비용

실제 계정·검색 API·호스팅 계정이 없으면 외부 기능이 켜지지 않습니다. 실제 발송 성공을 주장하지 않습니다. 로그인·DB는 로컬 테스트에서 검증했으며 배포 후 HTTPS 쿠키·OAuth 리디렉션·영구 저장소 재시작 복구·제공자 정책을 다시 검증해야 합니다.

서버/영구 디스크는 Render의 배포 시 요금이 적용됩니다. 무료 GitHub Pages는 데모 전용입니다. Gmail 계정/Workspace, 검색 API는 선택한 제품에 따라 요금이 달라집니다. Google 제한 범위 검증·보안 평가, Meta 앱 심사 대응은 추가 준비가 필요할 수 있습니다. API 심사 완료나 사업·법률 요건 적합성을 코드 구현으로 대신할 수 없습니다.

아직 미구현: 복수 관리자·권한 역할 UI, 비밀번호 재설정/MFA, 계정 초대, 자동 백업·복원 UI, 공급자 토큰 취소 API, 자동 Gmail push 알림, 대규모 작업 큐·페이지네이션 수집, AI 답장 생성, 무단 공개 플랫폼 크롤링. 운영 초기에는 단일 관리자·소규모 수동 승인 워크플로로 사용해야 합니다. 실제 외부 계정 발급·배포·본인 수신자 송수신 검증이 끝나기 전에는 완전한 실운영 준비 완료로 보지 않습니다.

암호화 키와 DB 백업을 분리 보관하고, 렌더 디스크 백업/복원 절차를 검증한 후 중요 협상 자료를 올리세요. 제한·수신 거부·승인 검사는 서버에서 실행합니다. DB 자체 전체 암호화는 구현하지 않았고, OAuth 토큰만 AES-256-GCM으로 암호화합니다. 호스팅 디스크 암호화·접근 통제는 배포 환경의 정책을 확인해야 합니다.
