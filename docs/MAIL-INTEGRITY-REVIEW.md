# 산지 발송 무결성 수정 — 승인된 운영 적용

실제 발송 서비스는 DOTHEGY/sanji의 Supabase bright-function이다. Creative OS B2B 저장소나 서비스를 원인으로 추정하지 않았다. 실제 운영 조회는 읽기 스냅샷으로 보관했고, 원본 메시지·수신자·기사 제목·게시판 제목의 저장 경로를 재현했다. 개인 업무 데이터가 포함된 상세 스냅샷과 10건의 본문은 저장소에 커밋하지 않고 `/workspace/results/sanji-mail-audit/`에 보관한다.

## 확인된 원인

1. 공개 검색 결과의 기사 제목을 업체명으로 취급하고 기사 URL의 언론사 루트를 회사 홈페이지로 승격했다. 기사에서 브랜드를 발견하는 단계와 공식 연락처 확보 단계가 분리되지 않았다.
2. parseOfficialPage는 해당 사이트의 공개 이메일을 추출했지만, 그 사이트가 제안 브랜드의 공식 사이트인지 확인하지 않았다. prepare-contact는 승인 플래그만으로 후보 연락처에 verified=true를 기록했다.
3. 미리보기와 sendDraft는 위 verified 플래그·수신 거부·버전·중복만 확인했다. 회사–이메일 게시 관계를 최종 발송 직전에 재검증하지 않았다. 즉시/일괄/예약은 모두 이 sendDraft를 통과한다.
4. `/product/[^/]+`라는 넓은 상품 URL 판정이 `/board/product/list_photo.html`와 `/product/list.html`도 상품 상세로 취급했다. title에서 뽑은 ‘상품 사용후기’·‘제품구매’가 실제 제품으로 통과했다.
5. 생성 도입부와 사용자의 공통 본문 양쪽에 담당자 연결·크리에이터 자료 제공 문장이 있었다. 합칠 때 중복을 제거하지 않았다.
6. 짧은 `.co` 주소와 원래 `.co.kr` 주소가 함께 저장되었다. 짧은 주소의 context에도 전체 `.co.kr`이 들어 있어 부분 일치만으로 게시 근거를 잘못 연결했다. 당시 전체 HTML은 저장되지 않았으므로 원문 오타·mailto 오류·인라인 태그 분절 중 정확히 어느 것인지는 확정하지 않는다. `.kr`을 붙여 새 주소를 만들지 않는다.

7. 운영 DB 함수 정의도 직접 대조했다. 공식 고객센터로 게시된 support 주소까지 SQL 접두사 규칙이 거부하고 있었다. 이 일괄 차단을 제거하되 공식 게시 검증·개인정보/채용 제외를 유지한다.
8. DB 발송 예약 함수는 후보의 대표 이메일로 수신 거부를 판단했다. 실패한 대표 주소 때문에 정상인 다른 실제 수신자까지 막히지 않도록 회사 거절/수신 거부 상태와 실제 발송 주소별 제외를 분리했다. 모든 실제 수신자를 SQL에서도 재검증한다.

## 수정

- 공유 규칙 검증 모듈 mail-integrity.ts를 추가했다. 기사/언론사는 발견 출처로만 보관하고 공식 사이트 검색으로 분리한다. 브랜드/회사명·공식 사이트의 게시 문맥·이메일 전체 문자열이 일치해야 한다. 네이버/Gmail/운영 법인 도메인을 일괄 차단하지 않는다.
- 메뉴·게시판·카테고리·기사 제목을 제품명으로 거부하고 판매 상세 URL을 확인한다. 검색 색인만 있고 원문 제품을 확인하지 못한 경우는 검증된 브랜드 단위 제안으로 돌아간다.
- 중복 문단과 반복된 담당자 연결/자료 제공 문장을 제거한다. 기존 실적·규모·매출·투자 표현을 추가하거나 확대하지 않는다.
- prepare-contact, 새 초안 생성, 예약 생성, sendDraft에서 검증한다. 이미 저장된 낡은 승인 초안도 발송 전에 다시 검사하며, 예약 실패는 review_pending으로 분리한다. 실패 시 Gmail 토큰/발송 예약/전송보다 먼저 중단한다.
- 확정 영구 반송은 DSN의 정확한 수신 주소 단위로 제외한다. 같은 회사의 나머지 주소에 반송·전달 상태를 추정하지 않는다. 기존 suppression·중복 제한을 유지한다.
- API 목록에는 현재 검증 결과와 제외 이유를 읽기 전용으로 반영한다. 원본 발송·회신 자료를 수정하거나 다시 보내지 않는다.

## 운영 적용 범위 / 복구

사용자의 최종 운영 적용 승인에 따라 발송 무결성 코드와 DB 규칙을 적용한다. 확인된 영구 반송 주소 9개만 개별 제외하고 미발송 후보 2곳에 검토 표시를 적용했다. 신규 이메일 기본 추적과 Gmail 회신 동기화는 유지한다. 기존 발송을 다시 보내거나 자동 발송을 재개하지 않는다.

검토 범위: 코드/작은 review_pending 상태 마이그레이션, 확인된 반송 주소만 개별 suppression 등록, 미발송 연락처 보유 후보의 검토 표시. 만료 초안과 발송·회신 원본은 그대로 보관한다. 스냅샷에서 활성 예약 0건, 유효 미사용 초안 0건이어서 취소/재발송할 예약은 없다. 실제 변경 전 최신 데이터와 스냅샷 updated를 다시 비교하고 달라지면 중단한다.

복구: 배포 직전 Edge 번들·Pages 커밋·후보 JSON·기존 suppression을 백업한다. 신규 기능을 되돌릴 때 이전 코드로 돌아가기 전에 발송을 비활성화하여 오래된 코드로 잘못된 메일이 나가지 않게 한다. 후보 검토 표시는 동일 버전인 행에 한해서 백업으로 복원한다. 확인된 영구 반송 차단은 자동으로 해제하지 않는다. 원본 대화/발송 이력은 삭제하지 않는다. 추적·Gmail 동기화는 이 감사 롤백과 분리해 유지/중지할 수 있다.

검증은 HTML 캐시·규칙·실제 저장 스냅샷·Gmail DSN을 사용했다. 새 유료 API·수집 결제 없음. 제안·테스트·사과·재발송 없음. 실제 공급 가능 여부·전체 사이트 새 HTML 재수집·실제 새 이메일 발송 시험은 수행하지 않았다.
