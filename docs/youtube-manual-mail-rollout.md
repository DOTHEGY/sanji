# YouTube manual email: review and rollout boundary

This is a local review candidate, not an applied migration or proof of delivery. It proposes separate `youtube-manual-mail` and `youtube-manual-scheduler` functions; it does not replace `bright-function`, register a recurring trigger, restart collection, or send Instagram messages.

The proposal `supabase/proposals/youtube-manual-ledger.sql` creates three owner-scoped RLS tables for review batches, one-use recipient ledger entries, and operator-attested Gmail reviews. Browser roles have no direct access; a limited set of server-only security-definer functions handles transitions. The new function uses the existing project service role, encrypted Gmail connection and Gmail OAuth credentials. It needs existing `EMAIL_SENDING_ENABLED=true` and a new explicit `YOUTUBE_MANUAL_SEND_ENABLED=true`; neither gate is turned on by source code. It appends a new YouTube outbox item and email thread only after a verified Gmail acceptance receipt. Existing brand/Instagram rows, functions and settings are not changed by this proposal.

The current production campaign policy must be reviewed separately: the last read-only check showed `pending_review` and no classification source. No code may infer a nonmarketing classification or invent its grounds. A real approved classification and authorization source are required; marketing is intentionally blocked by this candidate. Existing approved template, image and Gmail signature remain server-revalidated.

The user clarified that the proposed campaign is a new unsolicited collaboration proposal to food creators for convenience-store steamed-bun distribution, not a response to a recipient request. This fact does not establish the legal classification or any recipient's consent. Public email availability, a business-contact label, and the sender's intention to collaborate do not by themselves establish prior opt-in. The current candidate must continue to block this campaign until its classification and a recipient-specific authorization or applicable exception are verified and recorded. Review the applicable Korean rules, including information-and-communications-network law Article 50 and its implementing rules, for prior consent and any specific exception, advertising identification, sender identity/contact information, and a free and effective refusal mechanism. Do not represent a speculative exception as established. Persist and honor refusals independently of the campaign cutoff. The official sources could not be verified in this execution environment; no legal conclusion or compliance certification is made here. If marketing is applicable, this candidate has no approved marketing implementation and must not be enabled by changing its classification to an allowed nonmarketing value. A separately reviewed implementation must verify the actual message and enforce the appropriate consent, notices and refusal handling before any send.

Before an eventual rollout, independently review exact SQL, runtime bundle and UI hashes and effective grants, verify the actual Gmail original-message links and bounded Gmail history behavior, validate the accepted thread and existing inbox synchronization, and run the real PostgreSQL concurrency and browser suites. The new function's gateway JWT setting and the two flags must be reviewed. No user email may be sent by a test; only an authenticated user's later explicit review and send click can invoke Gmail. A user's Gmail-source attestation is not proof of consent or delivery.

The isolated ledger prevents repeated sends within this manual work, including uncertain sends. It does not provide a shared atomic lock with other engines or direct Gmail. A new refusal can arrive between the last read and the external Gmail request. Gmail alias searches are bounded (100 messages/10 seconds per fingerprint); incomplete reads are held. Recent records of unverified work origin are held rather than asserted to be duplicates. `sending`/`granted` after interruption is shown as unknown; searching Gmail by message ID does not prove non-delivery and must not authorize an automatic retry.

Rollback should disable the manual gate, remove the UI entry or revert the UI release, and retain the new tables, accepted outbox/thread entries and unknown states for audit. Explicit cancellation changes only unsent reserved/held rows; granted/accepted/unknown must not be reset or deleted. Removing schema or altering historic records needs a separate reviewed plan. Never redeploy the previously rejected whole-server bundle as a workaround.

## Proposed next-day scheduling extension

`supabase/proposals/youtube-manual-schedule.sql` is a second, unapplied proposal after `youtube-manual-ledger.sql`. It adds one RLS-protected schedule table and service-only schedule, token-bound claim, continue and finish RPCs. It replaces the new, still-unpublished manual candidate's immediate claim with worker-token-only claims. It does not change an existing production brand-email function. It derives next-day 10:00 Asia/Seoul in PostgreSQL and compares that time to the time shown to the user, binds membership to the reviewed project and date, and revalidates original snapshot, source versions, refusal and deduplication before the provider grant. A claim interrupted after work begins is not reclaimed automatically. A worker processes at most five messages per invocation, resuming only if all attempted messages have a definite accepted or cancelled state. Cancellation affects unclaimed reservations; an already processing message can still be sent.

The additional `youtube-manual-scheduler` function is a local candidate, not an active schedule. It requires `YOUTUBE_MANUAL_SCHEDULER_ENABLED=true`, `YOUTUBE_MANUAL_SCHEDULER_TRIGGER_VERIFIED=true`, the two existing manual send gates, and a reviewed recurring server-side trigger. The verified flag is an operator attestation, not an automated proof that the trigger is currently healthy; it must be set only after the real trigger is independently checked, and missing or disabled flags block new schedules. `EMAIL_SENDING_ENABLED` is shared by other paths: if it is off, do not turn it on merely for this feature without independently assessing its effect on existing queues and engines. The Edge functions use the existing shared project service role and Secrets; this is not complete security isolation. No trigger, secret or flag was configured here. A 10:00 start is not a guarantee that all messages are sent at exactly 10:00; trigger frequency, runtime and provider limits govern completion.

The project's `net.http_request_queue` grants SELECT and schema USAGE to `anon` and `authenticated` and has no row-level security. Therefore the pg_cron/pg_net HTTP approach must not carry an authentication bearer in that queue, even when retrieved from Vault. A proposed GitHub Actions trigger instead requests a short-lived GitHub OIDC token for a fixed audience and calls the fixed scheduler HTTPS URL with redirects blocked. The scheduler verifies GitHub's RS256 signature and fixed issuer, repository and owner numeric IDs, exact workflow/ref, scheduled event, hosted runner, audience and short token lifetime. The scheduler function must have gateway JWT verification disabled because this is not a Supabase JWT, but its own authentication must stay enabled; owner-facing routes continue to require Sanji login. This adds GitHub `id-token: write` to the one workflow and requires GitHub JWKS network access; it creates no shared scheduler secret. Repository workflow write access and GitHub-hosted runner identity are part of the trust boundary, and actual claims, key rotation and network reachability need independent review and a safe live check before activation.

The workflow polls every five minutes from 10:00 through 11:55 Korea time and can consume existing Actions and Edge Function usage; remaining allowance and any cost are unverified. Its separately dispatched identity-health route accepts only a `workflow_dispatch` token and never calls the worker; the worker accepts only a `schedule` token. Failure stops the current invocation, not future workflow runs: an uncertain/processing batch remains non-retryable, while a later run can process a different due batch. A backlog left outside the two-hour window is not automatically processed until the next window and can expire. GitHub scheduled jobs may start late. This workflow and its flags have not been published or configured.

The existing product UI is based on a later main than this candidate. Integrate against current main and independently review the exact final diff and generated bundles before any deployment. The visible selection is exclusion-based and limited to one explicit project date; the confirmed server review binds project, date, owner, exact recipients, content and scheduled time. The worker's latest refusal check and the external Gmail call cannot be made one atomic transaction; a refusal may arrive in that gap. Existing daily-email classification remains `pending_review`, so this candidate stays blocked rather than silently changing policy or treating public contact data as consent. Neither actual consent nor delivery is established by a public source or Gmail acceptance.
